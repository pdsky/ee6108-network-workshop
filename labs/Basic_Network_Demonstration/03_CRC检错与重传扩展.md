# 差错控制扩展 CRC 检错与重传的基本区别

适用对象：一般工程背景、网络配置初学者。本模块作为可选扩展，安排 20 分钟，重点区分检错、重传与前向纠错。一天课程仍为 420 分钟：选择本模块时，用它替换最后教学段的 20 分钟加深练习；基础实验或个人评价未完成时，保留本模块供课后阅读。

## 软件能力与证据边界

Cisco 官方 PDU Information 帮助明确说明：仿真时可点击事件或信封，在 Inbound/Outbound PDU Details 查看按协议分组的字段；Ethernet/ARP 示例包含前导码、FCS、源及目的地址。因此 Packet Tracer 适合用来认识帧及 FCS 字段的位置。[Cisco 官方 PDU Information](https://tutorials.ptnetacad.net/help/default/mode_simulation_PDUinfo.htm)

官方 TCP 模型涉及序号、确认及未确认数据的重传；Algorithm Settings 还解释了未在设定时间收到确认时的重传行为。这能支持准备一个 TCP 确认或超时重传的教学场景。[Cisco 官方 Layer 4 Models](https://tutorials.ptnetacad.net/help/default/model_layer4.htm)、[Cisco 官方 Settings and Preferences](https://tutorials.ptnetacad.net/help/default/preferences.htm)

所用 Packet Tracer 9.0.1 的本机 help/default 文档和已查官方在线帮助，没有提供普通 GUI 用户逐位翻转以太网载荷、设定 BER 并观察 CRC 重算的操作说明。FAQ 说明其模型经过简化，部分真实接口错误统计并未建模。**本扩展采用纸上比特串完成检错，不依赖 Packet Tracer 注入线路比特差错。**这是已查官方资料支持的设计边界，不断言所有版本或自定义扩展都不可能实现。[Cisco 官方 FAQ](https://tutorials.ptnetacad.net/help/default/faqTroubleShoot.htm)

| 内容 | 本课使用方式 | 不应写成的结论 |
|---|---|---|
| 帧头与 FCS 字段 | 使用 PDU Details 观察字段 | 看到 FCS 就已经演示了物理误码或真实 CRC 计算 |
| CRC 单比特差错 | 用纸上比特串与模 2 除法，独立核验 | Packet Tracer 已真实注入线路 bit flip |
| TCP 确认 | 在预先跑通的 HTTP/TCP 场景中观察 ACK、Seq 等字段 | ICMP echo reply 就是 TCP ACK |
| TCP 自动重传 | 教师须事前实际试跑并记录同一连接、方向、序号范围与事件时间 | 点 Fire 重发 ping 就证明 TCP 自动重传 |
| ACL 丢弃 | 如需演示，说明是策略丢包 | ACL 改变了载荷比特、产生 CRC 差错或实现纠错 |

仅打开已有 ICMP 测试文件，不会自动得到 TCP 重传实验。Add Simple PDU 是图形化单次 ping 工具；手动再次发送属于用户重新发起测试。[Cisco 官方 Simulation Mode](https://tutorials.ptnetacad.net/help/default/mode_simulation.htm)

## 学生要区分的三件事

**CRC 检错**回答“收到的数据是否通过这项一致性检查”。真实以太网帧尾的 FCS 承载 32 位 CRC；校验不匹配说明内容不可信。本模块使用更短的教学多项式，便于手算，不能把下面 3 位余数当成以太网实际 FCS。[Cisco 对真实设备 CRC 的解释](https://www.cisco.com/c/en/us/support/docs/ios-nx-os-software/nx-os-software/217554-understand-cyclic-redundancy-check-crc.html)

**确认、超时和重传**解决“没有得到所需确认后，再发送一次”。发送方保留数据副本，在条件满足时重传；重传不等于把收到的坏比特直接修好。TCP 的确认号表示下一期待的字节序号；其校验和是 16 位反码校验和，不是以太网 CRC。[TCP 标准 RFC 9293 第 3.1 节及第 3.10.8 节](https://www.rfc-editor.org/rfc/rfc9293.html)

**前向纠错 FEC**利用预先发送的冗余，在所用码的能力范围内恢复错误或丢失的信息。ACK/超时重传不是 FEC，CRC 判错本身也不等于接收端已经恢复原数据。FEC 可与其他可靠性机制组合，但本节只要求辨认区别。[IETF 关于 FEC 与 ARQ 的说明 RFC 3453](https://www.rfc-editor.org/rfc/rfc3453.html)

## 独立手算例

约定：采用简化的 CRC 模型，不作反射、初值或末尾取反；减法使用 XOR，没有借位。生成多项式 G = 1011，即 x³ + x + 1，次数为 3，所以附加 3 位校验。真实标准有额外约定；例如 PPP 的 FCS-16/32 实现见 RFC 1662，本例不是其完整算法。[PPP 帧及 FCS 标准 RFC 1662](https://www.rfc-editor.org/rfc/rfc1662.html)

发送数据 D = 1101。

1. 给 D 末尾补 3 个零，得到 1101000。
2. 用 G = 1011 作模 2 长除法。将除数对齐当前最左侧的 1，逐位 XOR。
3. 得到余数 R = 001。
4. 用余数替换补入的零，发送码字 C = 1101001。

```text
1101000 XOR 1011000 = 0110000
0110000 XOR 0101100 = 0011100
0011100 XOR 0010110 = 0001010
0001010 XOR 0001011 = 0000001

余数取最后 3 位：001
发送码字：1101 | 001
```

接收端收到完整码字后，直接用同一个 G 除整个码字，不再补 3 个零。

| 接收情况 | 收到的码字 | 除以 1011 的余数 | 判断 |
|---|---|---|---|
| 正常接收 | 1101001 | 000 | 本检查未发现差错 |
| 从左数第 4 位由 1 翻为 0 | 1100001 | 011 | 检出差错，不接收这份数据 |

第二行的检验过程如下：

```text
1100001 XOR 1011000 = 0111001
0111001 XOR 0101100 = 0010101
0010101 XOR 0010110 = 0000011

余数：011，不为零
```

教师必须在“发送后”翻转原码字的一个比特，保留原校验位，不能按新数据重新生成 CRC。否则接收端看到的是重新编码的数据，不能表示传输期间损坏。

非零余数告诉本实验的接收端“有错”，本流程没有定位并修正错误的步骤；接收端不能凭这一判断通用地恢复 D。零余数应表述为“本检查未发现差错”，不能说“证明所有可能错误都不存在”。CRC 存在未检出错误的可能性，具体能力取决于生成多项式、长度和错误模式。[RFC 3385 的 CRC 检错讨论](https://www.rfc-editor.org/rfc/rfc3385.html)

教师选做反例：C XOR 0001011 = 1100010。它改变了 3 位，但用本教学 G 除后仍为 000，因为错误模式本身能被 G 整除。不要求初学者证明一般性质；用这个例子纠正“零余数绝对无错”的误解即可。

## 20 分钟扩展流程

| 时间 | 教师引导 | 学生行为与可观察结果 |
|---|---|---|
| 0–3 分钟 | 提问“收到了比特串，是否等于内容可信”，区分检错、重传和 FEC | 先判断，不提前给出完整答案 |
| 3–8 分钟 | 示范 XOR 和第一步，给出 D、G | 两人完成剩余长除法，得到 001 与发送码字 |
| 8–11 分钟 | 发正常卡与翻转第 4 位卡 | 计算或核对 000、011，记录判错，不能自行改回原串 |
| 11–15 分钟 | 用发送者、接收者及计时卡演示重传 | 坏码字被丢弃；没有所需 ACK，超时后发送原码字；有效接收后给 ACK |
| 15–18 分钟 | 有已验证的软件场景时观察 FCS 或 TCP 字段，否则比较三种机制与 ACL 丢弃 | 记录实际可见字段；说明策略丢包与比特翻转的区别 |
| 18–20 分钟 | 发两个出口问题，可用另一单比特翻转作个人检查 | 说清 CRC 负责检错；正确副本依靠重传；完成个人判断 |

纸上时序可以写成：

```text
发送方                       接收方
原码字 1101001 ──翻一位──→ 1100001
                             余数 011，丢弃
       等待所需确认……
       教学计时卡到期
原码字 1101001 ──────────→ 1101001
                             余数 000，接受
               ←───────── ACK
```

这是简化的停等重传角色演示，不是 Packet Tracer 产生的 TCP 跟踪记录。CRC 计算不自动发送 ACK；ACK、保存副本、超时与重传由另一个协议机制规定。真实以太网 CRC 失败，也不意味着以太网一定给发送方回一个 NAK；上层可靠传输可能把丢弃表现为丢包，再由其恢复机制处理。

压缩为 5 分钟时，教师直接给出已编码的 C，让学生核对两个余数，再做纸上重传与两道判断题。10 分钟时保留手算、单比特翻转、纸上重传和出口检查；15 分钟时增加字段观察或机制比较。压缩版本仍须讲清证据来自纸上模拟还是软件观察。HTTP 服务器与重传场景由教师事前准备，不让新手在这个扩展内同时新建服务、计算 CRC 和制造重传。

## Packet Tracer 字段观察的教师准备与步骤

以下操作用于教师准备字段观察。**这些新增 GUI 字段/重传操作尚未在本扩展中实测；本扩展没有附已验收的 CRC/TCP 重传 .pkt。**其他网络实验的 ICMP 成功不能作为这些操作的实测结果。

1. 教师事前在自己的副本中用一台 PC 访问已经配置并验证正常的 HTTP 服务器。优先按 IP 访问，避免把 DNS 故障混入本节。
2. 切换 Simulation，显示必要的 ARP/TCP/HTTP 事件，单步观察；点击相应 TCP 事件或信封，查看 PDU Details。
3. 让学生找出 Ethernet 源/目的 MAC 与 FCS，以及 TCP 的源/目的端口、序号、确认号与 ACK/SYN 标志。以当前实际显示为准，缺失的字段不要猜填。
4. 对每条记录写清源、目的、连接方向、Seq、ACK、标志与事件时间。ACK 标志与确认号需结合读取；不要把不同方向出现的同一数字视为重传。
5. 如教师要增加 TCP 丢包重传，必须事前试跑。优先让一次 TCP 建连受到策略阻断，以观察同一 SYN 序号范围的重复发送；它演示的是连接尝试的超时重传，不是已建立连接的数据段重传，更不是线路误码。持续阻断时不承诺最终成功。
6. 不建议在现场临时修改 ACL 来“丢掉恰好一个 ACK”：官方帮助说明配置改变可能重启可见仿真场景，事件记录可能被重置。只有已记录并复现的场景才能列为软件演示；否则用上述纸上时序保证学习目标。[Cisco 官方 Simulation Mode 场景重启说明](https://tutorials.ptnetacad.net/help/default/mode_simulation.htm)

仅有三次握手或正常 ACK，不足以证明观察到了重传。真正的软件证据至少应包含同一连接与方向、重复覆盖同一序号范围、事件时间，以及接收或丢弃原因；同时注明丢包由何种设置造成。ACK 报文丢失、数据丢失与比特差错不是同一种事件。

出口问题：

- CRC 检出差错后是否已经恢复原数据？标准答案：没有，本实验只判错并丢弃，未执行纠错解码。
- 超时后再次发送原码字是否属于 FEC？标准答案：不属于；这是反馈/计时支持的重传。
- ACL 丢弃能证明线路发生了 bit flip 吗？标准答案：不能；ACL 按规则放行或丢弃，不是此处定义的比特翻转。
- TCP Checksum 是否就是 Ethernet FCS？标准答案：不是；它们属于不同层、使用不同算法。

迁移小题：仍用 G = 1011，把正常码字从左数第 2 位翻转，得到 1001001。请独立算余数并判断。教师答案：111，检出差错。不要在学生版提前给出这项答案。

## 教师数学核验记录

以下 Python 示例在本机独立执行通过，验证了上述发送余数、两种单比特错误和选做反例。它是普通 Python 数学核验，不是在 Packet Tracer 设备脚本中执行，也不代表物理通信误码实测。

```python
def crc_rem(bits, poly):
    work = [int(x) for x in bits]
    divisor = [int(x) for x in poly]
    width = len(divisor)
    for i in range(len(work) - width + 1):
        if work[i] == 1:
            for j in range(width):
                work[i + j] ^= divisor[j]
    return "".join(str(x) for x in work[-(width - 1):])

assert crc_rem("1101000", "1011") == "001"
assert crc_rem("1101001", "1011") == "000"
assert crc_rem("1100001", "1011") == "011"
assert crc_rem("1001001", "1011") == "111"
assert crc_rem("1100010", "1011") == "000"
```

手算结果已由上述 Python 独立核验。原生 GUI 的 CRC 注错未被官方帮助确认，新增 TCP/HTTP/重传操作未实测。授课时分别记录纸上计算、实际软件观察与个人出口题；正式报告只报告已取得的技术和教学证据。
